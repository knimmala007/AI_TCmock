# 0013. Signatures of the remaining tools, the ok rule and the permanent transport codes

Status: accepted (Oct 28 2026), from ticket 024. It completes ADR 0008. Facts and options: the read-only memo for ticket 024 (not stored in the repo).

## Context
ADR 0008 fixed the envelope, `save_answers`, `ask_broker`, `explain_form` (source only), `request_approval` and the next-question rule. The inputs, outputs and errors of `get_deal_status`, `flag_missing`, `acknowledge_disclosure`, `mark_clear_to_close` and `explain_form` were open, and so was the meaning of `hand_off`. Three things in the merged code differed from the docs: a read tool returns `ok: true` although ADR 0008 said `ok` meant "stored"; `save_answers` reports every refusal per fact; the loop turns bad arguments into plain text, not an envelope code.

## Decision
1. **The ok rule.** A tool's `ok` is true when it did what was asked: a write stored something, a read returned data, or what was asked was already true. A refusal or a decline is `ok: false`.
2. **`get_deal_status`** (seller, buyer, lender) stays an alias of `get_deal`: the same handler, the role's view, no `inbox`. Release-based filtering (ticket 047) is added in the one view function.
3. **`flag_missing`** (broker) is a read-only report in the broker's own turn. It is per form, built from the `DOCS` fields that have no value on the deal, with the deal's `never_received` entry attached to a field that has one. It persists nothing. A required form with no template is listed in `flagged_forms` by code only, with no missing-field list. Unanswered seller certifications are listed as awaiting the seller (ADR 0010). Errors: `NOT_FOUND`, `UNTESTED_JURISDICTION`, `ROLE_FORBIDDEN`.
4. **`explain_form`** (seller, buyer, lender): input `{code}`. The text is repo text only: the `DOCS` metadata (`name`, `form`, `src`) and the `q` and `why` text of the questions that feed the form. No model-written law and no deal values. A code the role may not see is `ROLE_FORBIDDEN`; a code the role may see but the deal does not require is `FORM_NOT_REQUIRED`. A visible code with no template returns `ok: true` with `has_template: false` and a fixed flag-only note.
5. **`acknowledge_disclosure`** (buyer): input `{code}`. It appends `{form, by, at}` to `deal.acknowledgements`, an append-only list. It runs no snapshot or lock check, because it does not change a form. It is allowed only for a form in the buyer's view (its own forms, plus forms delivered to it, see 8); anything else is `ROLE_FORBIDDEN`. A repeat returns `ok: true` with `already: true` and the original time, and writes nothing.
6. **`mark_clear_to_close`** (lender): no input. It records `deal.loan.clear_to_close = {by: "lender", at}`. It changes no stage and has no stage gate. `FORM_NOT_REQUIRED` only when `APPR` is not required for the deal. A repeat is idempotent as in 5. The lender session's own statement counts as the attestation (ADR 0010 extension), with the demo-mode caveat: until real sign-in (ticket 057) anyone can pick any role.
7. **`request_approval` and `hand_off`, as built in 043.** `request_approval` records one pending hand-off request per action; a newer request replaces it. It sets no lock and sends no notice; the broker sees it through `GET /api/approve`. `hand_off` is assignment only: it appends `{from, to, forms, at, approval}` to `deal.handoffs`, uses up the grant, and changes no access, form, stage or lock. The seller needs no release. A buyer or lender needs the forms released first (ticket 047). Refusing forms with no template in both tools is ticket 043c.
8. **Disclosure delivery (widening).** The buyer cannot see seller disclosures today (TDS, SPQ, NHD and AVID are seller-side). A seller-side form becomes visible to the buyer only through a separate list, `deal.delivered[role]`, written only by the broker's Release click: a human action on the server, never a model-callable tool, never by `hand_off`. It grants read access only; write access (`save_answers`) stays decided by `canAccessForm`. **Open, to be decided in ticket 047's plan:** which forms qualify, and whether the buyer sees the full content or only a receipt.
9. **Batches are per fact.** Every refusal in a `save_answers` batch (role, required, snapshot, lock, no template, and the value checks) is reported per fact by position. A batch of one returns the single-fact shape. A batch stores the facts that pass; nothing is stored only if every fact is refused.
10. **Transport codes.** `NOT_FOUND`, `NO_TEMPLATE`, `UNTESTED_JURISDICTION`, `QUESTION_TOO_LONG`, `INBOX_FULL` and `NO_PENDING_REQUEST` are permanent transport codes. The ten status codes stay ten. `UNKNOWN_TOOL`, `BAD_ARGS` and `TURN_LIMIT` are plain-text tool errors, not envelope codes; the one exception is `BAD_ARGS` inside a batch's per-fact results.

## Reasoning
The code already behaves this way and is tested; the rule that `ok` means "did what was asked" matches it and keeps one failure path in the loop. Repo text keeps explanations free of model-written law. An append-only acknowledgement list keeps history like `deal.handoffs`. A separate delivered list keeps read access from being granted by a model-callable path.

## Consequences
- ADRs 0008, 0010 and 0011 are amended to match. ADR 0002 is not changed.
- The spec's Tools section, CONTEXT "Still open" item 1 and reminders R9, R20, R24 and R28 are updated.
- Tickets 040, 051, 053 and 055 build against these signatures. 053 now depends on 047, because the buyer needs a delivered form to acknowledge. Ticket 043c refuses untemplated forms in the approval tools. Ticket 047 takes the open delivery questions.
